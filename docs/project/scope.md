## 1. 기존 시스템에 어디까지 관여하나

원칙: **읽기는 넓게, 쓰기는 사람이 확정한 뒤에만, 외부로 나가는 발송은 에이전트가 하지 않는다.**

| 연동 대상 | 에이전트가 하는 것 | 하지 않는 것 | 사람이 정하는 지점 | 근거 |
| --- | --- | --- | --- | --- |
| 메일플러그 (회사 메일, IMAP) | 받은·보낸 메일 읽기. 읽음 표시도 바꾸지 않음 | 발송·삭제·이동 | — | D-014, [`mailplug.md`](mailplug.md) · 구현 예정 (회사 개통일 회신 대기) |
| Gmail (선택) | 메일 읽기 → 메일 분석·회의록 초안 | 자동 발송 | 답장은 사용자가 내용을 보고 직접 보낼 때만 (1학기 기능) | 규칙 2 |
| 미팅 메모 | 회의록 초안 | 원본 수정·영구 삭제 (보관만) | 회의록 확정·보관 | D-020, D-025 |
| 인물 대장 (우리 DB) | 같은 사람 후보 최대 3명 제안 | 병합·신규 등록 | 후보 고르기, 병합(되돌리기 가능) | D-022, D-025 |
| 할 일 | 초안 추출, 부류·기한 제안 | 일괄 확정 | 하나씩 확정 | D-023 |
| Google 캘린더 | 확정된 일정 등록·수정·삭제 | 확정 전 등록 | 일정 확정, 삭제 (누가·언제 기록) | D-014, D-025④, D-026 |
| 세일즈맵 | 확정된 일정을 등록 (캘린더와 함께) | 확정 전 등록 | 등록 요청 | 지금은 모의 모드(`SALESMAP_API_MODE=mock`), 실제 연결은 회사 확인 후 |
| 외부 메시지 (메일·안내문) | 발송 대기함에 초안까지 | 자동 발송 | 사용자가 직접 발송 | 규칙 2 |
| 알림 | 하루 1회 묶음 브리핑 | 즉시 알림 하루 3건 초과 | — | 규칙 6 |
| LLM | 로컬 모델(Ollama)로 분석. 메일·메모가 회사 밖으로 나가지 않음 | 유료 API 기본 사용 | 유료 API는 관리자가 켤 때만 | D-019, D-027, 규칙 7 |

## 2. 필수 vs 확장

**필수** = 11/30 실사용 버전에 반드시 들어가는 것 (회사 요청 5개, D-013) + 지켜야 할 원칙. **확장** = 필수가 돈 뒤에 프로젝트를 풍부하게 하는 것. 학습 모델은 기준(규칙)을 이길 때만 교체한다.

| 구분 | 기능 | 담당 | 상태 |
| --- | --- | --- | --- |
| 필수 ① | 미팅 정리: 메모·메일 → 표준 회의록, 3단 확인 화면 | B | ✅ |
| 필수 ② | 할 일·담당·기한 추출, 하나씩 확정 | C | ✅ |
| 필수 ③ | 사람별 미팅 이력: 상대 식별 + 이력 화면 | A | 🔄 식별 API까지, 인물 대장·연결 남음 |
| 필수 ④ | 할 일 진행 상태·사전 알림: 할 일 보드, 상태 자동 변경, 아침 묶음 | C, D | 🔄 보드·브리핑 API, 자동 변경 규칙 남음 |
| 필수 ⑤ | 다음 미팅 준비 안내: S-01 미팅 전날 브리핑 | D | ⬜ 5주차 |
| 필수 | 회사 메일(메일플러그) 수집 | 총괄 | ⬜ 회사 회신 대기 |
| 필수 원칙 | 사람 확인 후 확정, 수정 기록, 알림 묶음, 로컬 LLM, 데이터 결정 권한 | 전원 | ✅ 규칙·결정 (D-022~D-026), 수정 기록 API |
| 확장 | ML-1 같은 사람 판별 학습 모델 | A | 예정 |
| 확장 | ML-2 할 일 분류 학습 모델 | C | 규칙이 앞서 규칙 유지 |
| 확장 | ML-2 비교용 LLM 직접 판정 | B | 🔄 5주차 |

| 확장 | S-02 출장 준비, S-03 계약 서류 대조 | D | 여유 시 |
| 확장 | S-04~S-10 준비 서비스 명세서 | D | 명세만 |
| 보류 | 녹음 → 텍스트(STT) | B | 추가 검토 (D-015) |

## 3. 기존 방식과 무엇이 다른가 (비교표)

> 칸은 방식별 일반적인 모습. 발표 전에 방식마다 대표 제품 2~3개로 칸을 확인해 고친다 (제품 이름은 발표 자료에서만 쓴다).

| | 수기 메모 + CRM 직접 입력 | 녹음 기반 AI 회의록 도구 | CRM 내장 AI 요약 | 범용 AI 챗봇에 붙여넣기 | **우리** |
| --- | --- | --- | --- | --- | --- |
| 입력 | 사람이 전부 입력 | 미팅 녹음 (고객 동의 필요) | CRM에 쌓인 기록 | 사람이 복사해 붙여넣기 | 미팅 메모·메일 (메일은 자동 수집) |
| 상대가 누구인지 | 사람 기억 | 화자 구분 위주 | CRM 연락처 기준 | 없음 | **이름·연락처·소속으로 후보 3명 제시, 동명이인 구분** |
| 회의록 항목 근거 | — | 녹음 구간 | 보통 없음 | 없음 | **항목마다 원문 근거, 모르면 빈 칸** |
| 할 일·기한 | 사람이 정리 | 요약 속 할 일 목록 | 일부 | 요청하면 | 무엇을·누가·언제까지, **기한은 규칙으로 계산** |
| 할 일 종류별 준비 안내 | — | — | — | — | **11부류 판정 → 미팅 전날 브리핑 등 준비 안내** |
| 확정 | 사람 | 대개 자동 저장 | 대개 자동 | 사람이 옮겨 적음 | **사람이 하나씩 확정, 고친 값은 수정 기록** |
| 데이터가 회사 밖으로 | 안 나감 | 대개 외부 서버 | CRM 서버 | 외부 서버 | **안 나감 (로컬 LLM)** |
| 추가 비용 | 입력 시간 | 구독료 | 상위 요금제 | 구독료·입력 시간 | 무료 모델 (PC 자원) |
| 쓸수록 나아지나 | — | 제품 업데이트 | 제품 업데이트 | — | **사람이 고친 기록이 재학습 정답** |

발표 문장: "메모를 회의록으로 바꾸는 도구는 많지만, 저희는 상대가 누구인지 식별하고, 할 일을 업무 종류별 준비 안내까지 이어 주며, 모든 확정은 사람이 하고 데이터는 회사 밖으로 나가지 않습니다."

## 4. 새 회사에 도입할 때 설정할 것

| 항목 | 지금 | 회사마다 바꿀 것 | 바꾸는 방법 |
| --- | --- | --- | --- |
| 메일 계정 | Gmail 연결 있음, 메일플러그 예정 | 회사 메일 서버, 관리자의 IMAP 허용, 앱 비밀번호 | 설정 화면 (메일 계정) |
| 캘린더 | Google 계정 연결, 기본 캘린더·서울 시간대 | 쓸 캘린더 | 설정값 (`GOOGLE_CALENDAR_ID` 등) |
| CRM (세일즈맵) | 연결 주소 설정값, 지금은 모의 모드 | 회사 CRM 주소·인증 | 설정값 (`SALESMAP_API_*`) |
| 회의록 양식 | 5문항 + 경량 3필드 고정 (D-009) | 회사 회의록 양식 | **코드·데이터 형식 변경 필요** (팀 합의) |
| 할 일 부류 | 11부류. S-04~S-10은 인력 파견 업무 전용 | 업종에 맞는 부류만 쓰기·추가 | **지금은 규칙 코드**. 켜고 끄는 설정 필요 |
| 인물 대장 | 비어서 시작 | 기존 고객 명단 가져오기 | 없음 (가져오기 기능 필요) |
| 알림 | 하루 1회 묶음 | 브리핑 받을 시간 | 설정 화면 (알림 시간, 예정) |
| LLM | `qwen2.5:7b` (RAM 약 4.7GB) | PC 사양에 맞는 모델 | 설정값 (`OLLAMA_MODEL`, 부족하면 3b) |
| 사용 범위 | 담당자별 분리 (D-025⑤) | 팀 공유·담당자 이관 여부 | 시범 운영 전 회사와 결정 |

**정리:** 대부분은 설정값과 연결 화면으로 끝난다. 회사마다 코드를 고쳐야 하는 것은 **회의록 양식**과 **할 일 부류** 두 가지라서, 시범 운영 전에 회사 양식·업무 목록을 받아 맞춘다.

## 5. LLM 모델에 묶여 있지 않은가

- 모델은 설정값 하나(`OLLAMA_MODEL`)로 바꾼다. 같은 평가셋·같은 코드로 로컬 모델 4종을 돌려 모두 동작했다 (LLM 성공률 100%, [`MODELS.md`](../../ai-module/eval/MODELS.md)).
- 점수는 과제마다 1등이 달랐다: 메일 분석은 `qwen2.5:7b` 81.0%, 회의록은 `gemma4:e4b` F1 83.8%. 두 과제를 다 이기지 못해 기본값을 유지했다 (D-027).
- 모델이 실패해도 멈추지 않는다: 메일 분석은 규칙 결과로 돌아가고, 회의록은 빈 초안 + 실패 이유를 보여 사람이 쓴다.
- 날짜·기한·상태처럼 규칙으로 되는 것은 LLM을 쓰지 않아 모델과 무관하다 (규칙 4).

## 6. 데이터 결정을 사용자가 전권으로 갖는가

예. 데이터 상태를 바꾸는 결정(확정·병합·신규 등록·보관·삭제)은 **사용자가** 하고, 에이전트는 제안만 한다. 원본·확정본은 "삭제"해도 숨김(보관)만 하고, 사람의 결정은 수정 기록 또는 누가·언제 기록으로 남는다. 자세히 D-025·D-026.

## 7. 사람 확인(human-in-the-loop) 성능 평가 계획

| 지표 | 무엇을 보나 | 데이터 | 상태 |
| --- | --- | --- | --- |
| 무수정 승인률 | AI 초안을 고치지 않고 승인한 비율 (에이전트·항목별) | 수정 기록 (`ACCEPTED` vs `EDITED`) | 기록은 쌓이는 중, 집계 필요 (D) |
| 항목별 수정률 | 어느 칸을 사람이 많이 고치나 (약속·다음 접촉·할 일 기한 등) | 수정 기록의 대상 칸 | 집계 필요 (D) |
| AI만 vs AI+사람 | 정답 대비 F1: AI 초안 vs 사람이 확정한 결과 | 평가셋 + 확정본 | 시범 운영 때 |
| 확인 시간 | 초안을 열어 확정할 때까지 (목표 건당 3분) | 화면에서 연 시각·확정 시각 | **기록 없음 → 추가 필요** (B 화면) |
| 처음부터 작성 vs AI 초안 확인 | 같은 메모로 시간·정확도 비교 | 팀원 또는 시범 사용자 | 시범 운영 때 |
