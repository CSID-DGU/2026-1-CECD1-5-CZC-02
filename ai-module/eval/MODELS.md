# 모델 비교표

같은 평가셋·같은 지표로 모델 설정을 바꿔 돌린 결과를 한 장에 모은다. 도구는 `eval/bench.py`, 설정 목록은 `eval/bench_configs.json`, 원자료는 `eval/results/bench_<시각>/`(git에 안 올라감).

## 규칙

- 모델은 **환경 변수로만** 바꾼다 (`app/config.py`). 코드에 모델 이름을 박지 않는다.
- 지금 기본값이 **기준**. 새 모델은 기준을 **이길 때만** 교체한다. 지면 기준 유지 + 이유를 아래 "판단 기록"에 남긴다.
- 정확도만 보지 않는다: 정확도 · 건당 시간 · 메모리/GPU · 비용(1,000건당) · 데이터를 외부로 보내는지.
- 유료 API(OpenAI)는 `--allow-paid --limit N`을 줘야만 돈다. CI·테스트에서는 호출하지 않는다. 데이터는 가짜 평가셋만.
- 교체하면 `docs/project/decisions.md`에 한 줄 + 기본값 변경 PR. 다른 사람 부품에 영향을 주는 교체(임베딩 → A·C, NER → A)는 담당자와 합의 후.
- 모델 교체 결정은 **11/20까지**.

## 실행 (ai-module 폴더에서)

```bash
python -m eval.bench --list                                         # 설정 목록
python -m eval.bench --write-md                                     # 기본 대상(무료) 실행 + 아래 표 갱신
python -m eval.bench --only ollama-qwen2.5-7b --write-md            # 골라서
python -m eval.bench --only openai-analysis --allow-paid --limit 10 --write-md   # 유료 (소량)
```

후보를 늘리려면 `bench_configs.json`에 `env`만 다른 설정을 추가한다. 자동 표는 이번에 돌린 설정의 행만 바꾸고 다른 행은 남긴다.

## 지표 읽는 법

- **무수정 통과**: 한 메일의 채점 필드가 전부 맞은 비율 (사람이 고칠 필요 없음). 메일 분석의 대표 지표
- **LLM 성공률**: LLM을 시도한 메일 중 실제로 LLM 결과가 쓰인 비율. 규칙이 비영업으로 판정한 메일은 원래 LLM을 건너뛰므로 빠진다. 100%가 아니면 Ollama 꺼짐·타임아웃 등으로 규칙 폴백이 섞인 것이라 그 행은 LLM 성능이 아니다 (⚠ 표시)
- **메모리**: 프로세스 = 평가 프로세스 최대 메모리(GLiNER·임베딩 모델 포함), 모델 = Ollama에 올라간 모델 크기와 GPU 비율
- **건당 시간**: 평균 · 중앙값. 평균에는 첫 건의 모델 적재 시간과 LLM을 건너뛰는 비영업 메일이 섞이므로 중앙값도 함께 본다. 평가 PC에서 잰 값이라 다른 PC 결과와 섞어 비교하지 않는다
- **기준 고정**: 설정에 적지 않은 모델 변수는 `app/config.py` 기본값으로 돌린다 (로컬 `.env` 무시)
- n이 작으면(특히 유료 `--limit`) 한두 건 차이로 크게 흔들린다

10/14에 기본값이 7b로 바뀌어(D-019) 행 이름을 바꿨다 (`ollama-default` = 7b, `ollama-qwen2.5-3b` = 이전 기본값). `rule`·`ollama-qwen2.5-3b`는 10/13 실행 그대로.

결과는 모두 총괄 PC(Windows, Ryzen 5 5500U·RAM 23.4GB, Ollama가 GPU 없이 CPU로 실행)에서 잰 값. 프로세스 메모리는 Windows에서 `psutil`이 없으면 비어 있다. 11/02 `ollama-default` 메일 시간(21.8s)은 모델 내려받기와 겹쳐 10/13(16.9s)보다 느리게 나왔다 — 정확도는 같다.

**L-2 후보 (11/02, seed 42)** — 설정은 `bench_configs.json`의 `ollama-qwen3.5-4b`·`ollama-gemma4-e4b`·`ollama-kanana-1.5-8b`(회의록은 앞에 `minutes-`). 메모리 칸은 Ollama `/api/ps` 값인데 gemma4는 실제보다 작게 나와, 모델만 올린 상태에서 `llama-server` 프로세스 메모리를 따로 쟀다(문맥 4096): 7b 4.7GB · qwen3.5:4b 3.4GB · kanana 5.2GB · **gemma4:e4b 6.9GB**.

- `qwen3.5:4b`(Apache-2.0), `gemma4:e4b`(Apache-2.0)는 생각 모드가 기본으로 켜져 있어 `OLLAMA_THINK=false`로 돌렸다. 켜 두면 생각 글이 출력 한도를 먹어 응답이 빈다. 비워 두면 think 값을 보내지 않으므로 qwen2.5 등 기존 모델은 그대로다.
- kanana 1.5 8B는 카카오 공식 원본(Apache-2.0)의 **비공식 GGUF 변환본** `hf.co/DevQuasar/kakaocorp.kanana-1.5-8b-instruct-2505-GGUF:Q4_K_M`으로 쟀다. 파일 4,920,765,472바이트, sha256 `f7ae0cc1de2396647dce4a82fb4943136bcc785339ee8944c6818184c983d287`(HF 파일 값과 일치), Ollama ID `a47ae444b176`. 비교 평가용이다.
- 메일 분석에서 gemma4가 7b보다 더 틀린 3건은 제품명을 줄여 쓴 것(`재고관리 자동화 솔루션` → `재고관리 솔루션`·`신규 솔루션`, `ESG 탄소배출 관리 플랫폼` → `ESG 플랫폼`, green-2는 참석자 1명 누락도)이다. noise-6·8·9 비영업 오분류는 네 모델 공통.

아직 없는 평가: 개체명(L-3에서 정답셋 작성), 할 일 분류(C 평가 데이터). 평가 스크립트가 `--engine/--limit/--output/--allow-paid`를 받고 `summary`·`runtime`·`usage`가 든 JSON을 쓰면 `bench.py`의 `TASKS`에 추가해 같은 표로 모을 수 있다.
