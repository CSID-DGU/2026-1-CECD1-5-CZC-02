# A — 같은 사람 판별 규칙 초안

작성: 2026-10-15. 상태: **설계 초안·내부 비교/검색/순위/평가 구현·팀 검토 전**.
기준: AGENTS.md, 최신 decisions.md, person.schema.json, identity_resolution.schema.json.

## 1. 무엇을 비교하는가

메일·메모의 인물 단서 하나를 Person 대장과 비교해 연결할 사람을 찾는다.
같은 이름의 사람이 있을 수 있으므로 이름 하나로 확정하지 않는다.
이번 언급을 기존 인물에 **연결**하는 것과 대장의 두 인물을 **병합**하는 것은 다른 작업이다.
판별기는 연결 후보를 제안하며 인물 대장을 병합·수정·등록하지 않는다.

입력은 계약의 mention과 Person 목록이다.
ML 실험의 label·caseType·personIdA/B·pairId·sourceRef·evidence는 비교 점수의 입력으로 쓰지 않는다.
sourceRef와 evidence는 원문 추적·검수에만 사용한다.

## 2. 표기 차이만 정리하기

정규화는 같은 정보를 같은 모양으로 정리하는 작업이다. 원문 자체는 보존한다.

| 항목 | 비교 전 처리 초안 | 임의로 하지 않을 처리 |
| --- | --- | --- |
| 이름 | 유니코드·앞뒤 공백 정리, 확인된 직함·호칭을 이름 경계에서 제거 | 이름 중간 글자 삭제, 성만으로 전체 이름 추측 |
| 영문 이름 | 공백·대소문자 차이 정리, 등록된 nameVariants와 비교 | 한글 이름에서 영문 표기를 자동 추측 |
| 회사 | 앞뒤·반복 공백과 표기 형식 정리 후 정확히 비교 | 서로 다른 회사를 유사한 이름만으로 합침 |
| 이메일 | 앞뒤 공백 제거, 도메인 대소문자 정리 | 계정 부분의 점·+태그 삭제, 공용 계정을 개인 계정으로 단정 |
| 전화번호 | 명시된 구분자 정리. 국가 정보가 확인된 경우에만 국내·국제 표기 대응 | 국가·내선 추측, 불완전 번호를 완전한 번호로 보충 |
| 누락 값 | null·빈 배열은 정보 없음으로 처리 | 빈 값끼리 일치 점수를 부여 |

영문·이메일 정규화 범위는 구현 테스트에서 구체화하며 원문 값을 덮어쓰지 않는다.

## 3. 같은 사람을 지지하는 단서

| 단서 | 초기 해석 |
| --- | --- |
| 이메일·전화번호가 같은 인물에 함께 일치 | 가장 강한 후보 단서. 공유·재사용 여부도 확인 |
| 이메일 또는 전화번호 한 가지 일치 | 강한 후보 단서. 이름·소속과 모순되는지 확인 |
| 대표 이름/등록 별칭 + 현재 회사 일치 | 동명이인을 좁히는 근거. 같은 회사의 동명이인 가능성은 남음 |
| 대표 이름/등록 별칭 + 이전 회사 일치 | 소속 이동 후보. 과거 소속이라는 사실을 근거에 표시 |
| 이름 오타·유사 표기 + 회사 일치 | 약한 후보 단서. 어느 글자가 다른지 원문과 함께 표시 |
| 이름만 일치 | 동명이인 가능성을 설명하며 다른 단서를 함께 비교 |
| 회사·직함만 일치 | 특정 사람을 식별하기에 부족함 |

이름 유사도는 두 문자열이 얼마나 비슷한지 나타내는 값이며 동일 인물 확률이 아니다.
현재 가짜 이름은 공통 접두어가 길기 때문에 유사도만으로 다른 번호의 사람을 연결하면 안 된다.
이름이 같더라도 채널이 같다는 이유만으로 추가 신뢰를 부여하지 않는다.
최근 접촉 시각 같은 입력이 없다면 “최근 미팅 상대”라는 근거를 만들어내지 않는다.

## 4. 충돌·모호함 처리

1. 같은 연락처가 여러 Person에 있으면 공용·중복 연락처 가능성을 reasons에 표시한다.
2. 이메일은 인물 A, 전화번호는 인물 B에 일치하면 충돌을 표시하고 자동 확정하지 않는다.
3. 이름은 같지만 회사가 다르면 이전 소속 이력을 확인한다. 회사가 다르다는 이유만으로 다른 사람이라고 단정하지 않는다.
4. 연락처는 같지만 이름이 다르면 공용·잘못된 입력·변경 가능성을 사람이 확인한다.
5. 약한 단서로 후보가 많이 동점이면 personId 순서로 앞선 사람을 더 확실한 사람처럼 표시하지 않는다.
6. 정답이 후보 3명 밖에 있을 수 있으므로 향후 확인 화면에는 추가 단서·기존 대장 검색이 필요하다.

예: 서로 다른 두 인물이 `가상인물_0001`이라는 이름을 사용하면 회사·연락처를 함께 본다.
`가상회사_001`에 있었던 사람이 현재 `가상회사_002`에 있다면 companyHistory가 이동 단서다.
이전 회사를 언급했다고 새 사람을 자동 생성하거나 현재 소속을 덮어쓰지 않는다.

## 5. 후보 순서와 점수

초기 순서는 연락처 일치와 충돌 여부 → 이름·등록 별칭 → 현재/이전 소속 → 보조 유사도 순으로 설계한다.
직함은 보조 정보이며 단독 식별 근거로 사용하지 않는다.
정확한 가중치·임계값은 아직 정하지 않았다. train에서만 정하고 eval은 고정된 버전의 평가에 사용한다.
후보는 최대 3명이며 같은 점수일 때의 표시 순서는 기술적인 동점 처리일 뿐 확률 차이가 아니다.

**계약의 candidates[].score는 동일 인물 확률로 설명돼 있다.**
임의 규칙 점수를 0~1로 바꿨다고 확률이 되지 않는다.
내부 순위 점수를 외부 score로 그대로 내보내는 방식은 합의 없이 채택하지 않는다.
보정된 확률을 어떻게 만들지 또는 기준 모델 점수를 어떻게 표현할지 팀 검토가 필요하다.
필드 추가·이름 변경 등 계약 변경이 필요해지면 구현 전에 멈추고 먼저 공유한다.

## 6. 판정 결과와 팀 확인 사항

| 상황 | 계약상 상태 | 이번 초안 |
| --- | --- | --- |
| 근거 있는 후보가 있음 | CANDIDATES | 최대 3명과 reasons 제안. 선택 전 personId=null |
| 비교할 단서가 있고 일치 후보를 찾지 못함 | NEW | 신규 등록 제안일 뿐. 사람 확인 전 등록하지 않음 |
| 비교 단서 자체가 부족함 | 별도 보류 상태 없음 | NEW에 포함할지 팀 검토. 새 상태를 임의로 추가하지 않음 |
| 기존 인물 연결이 확정됨 | CONFIRMED | 자동 연결 허용 조건과 사람 확인 범위를 먼저 합의 |

계약에는 CONFIRMED의 “자동 연결” 설명과 에이전트가 단독으로 확정하지 않는다는 원칙이 함께 있다.
**초안은 사람 선택 후 연결 확정을 제안하며, 자동 확정 조건은 임의로 구현하지 않는다.**
CONFIRMED에는 personId가 필요하고, 사람이 선택했다면 decidedBy=HUMAN을 사용한다.
사람의 후보 선택·신규 등록 결과는 D의 Revision API에 기록한다. D 저장 기능을 A가 대신 만들지 않는다.
원문은 mention·sourceRef로 보존하고 후보별 비교 근거는 reasons로 전달한다.
계약에 없는 evidence 필드를 식별 결과에 추가하지 않는다.

## 7. 구현·평가 때 확인할 사례

- 현재 데이터: 호칭·영문·오타·소속 이동·소속 누락, 동명이인·같은 회사 반례.
- 추가 회귀 검사: 같은 회사 동명이인, 공유 연락처, 이메일/전화 충돌, 빈 값끼리 일치 방지.
- 짧은 이름·공통 접두어·연락처 없는 입력을 억지로 맞히지 않는지 확인.
- 채워진 근거가 실제 입력 값에서 나왔는지, API 출력이 계약에 맞는지 확인.
- 두 기록의 쌍별 판정과 전체 대장의 후보 top-3 재현율을 따로 측정.
- 자동 CONFIRMED를 출력하지 않는 버전은 확정 정밀도 목표를 미측정으로 보고.
- 임베딩은 규칙 기준을 만든 다음 선택 기능으로 비교. 모델이 없으면 규칙으로 동작해야 함.

자동 확정 범위·NEW의 보류 의미·기준 모델의 score 표현은 팀 합의 후 구현한다.”

## 9. 구현된 표기 정리 사용법

`normalization.py`는 표준 라이브러리만 사용한다. `normalize_mention()`은 입력을 복사하므로
원문 mention은 그대로 남는다. 반환값은 내부 비교용이며 외부 응답의 mention에는 원문을 사용한다.
이 함수는 스키마 검증기나 동일 인물 판정기가 아니다.

- 이름: NFC 유니코드·공백·영문 소문자화. 공백으로 구분된 알려진 직함과 끝의 님을 제거한다.
  `가상인물_0001 부장님`은 `가상인물_0001`이 된다. 붙여 쓴 직함은 경계가 불명확해 유지한다.
- 회사: NFC·공백만 정리한다. 회사 약칭이나 법인 표기는 통합하지 않는다.
- 이메일: 앞뒤 공백·도메인 대소문자만 정리한다. 계정의 대소문자·점·+태그는 보존한다.
  @ 누락·중복과 내부 공백 등 지원하지 않는 입력은 None으로 둔다. 전체 이메일 유효성 검사는 아니다.
- 전화: 공백·하이픈·점·괄호만 제거한다. 국가번호 변환은 아직 지원하지 않는다.
  내선·마스킹·다른 문자가 있으면 일부 숫자만 추출하지 않고 None으로 둔다.
- None·공백은 정보 없음이다. 같은 None을 일치 근거로 쓰면 안 된다.
  입력의 선택 필드를 추가하지 않고 channel·sourceRef를 보존한다.

문자열이 아닌 값은 추측해서 변환하지 않고 TypeError로 알린다.
인물 대장의 이름·별칭·연락처도 같은 개별 정리 함수를 비교 시에만 적용할 수 있다.
Person 원본·이력·빈 배열을 변경하지 않는다.

`ai-module/`에서 `python -m pytest tests ml/identity app/identity -q`로 검사한다.
테스트는 원문 보존·과도한 통합 방지·가짜 비교 쌍 3,000개의 mention 계약을 검사한다.
현재 공용 CI의 tests/ 명령에는 A 내부 테스트가 포함되지 않아 총괄 검토가 필요하다.

## 10. 구현된 단서 비교 사용법

`features.py`는 스키마에 맞는 mention과 Person을 받아 내부 비교 자료를 반환한다.
새 모듈 간 데이터 형식이 아니므로 그대로 API 응답으로 내보내지 않는다.
추가 라이브러리·LLM·네트워크를 사용하지 않는다.

```python
from app.identity.features import compare_person, compare_people

comparison = compare_person(mention, person)
# comparison.name.status: MATCH / DIFFERENT / UNKNOWN
# comparison.company.matched_paths: ("companyHistory[0].company",) 등
comparisons = compare_people(mention, persons)
```

- name: 대표 이름과 등록된 nameVariants의 정확한 정규화 일치만 확인한다.
- email·phone: 대장의 연락처 목록 중 일치하는 값이 있는지 확인한다.
- company: 현재 소속과 이전 이력을 모두 확인하고 어느 경로에 일치했는지 남긴다.
- 각 단서는 observed에 언급 원문, registered에 비교 가능한 대장 값과 필드 경로,
  matched_paths에 일치한 경로를 보존한다. 입력 객체 자체는 바꾸지 않는다.
- UNKNOWN: 한쪽에 비교 가능한 값이 없다. 공백·미지원 연락처도 여기에 해당한다.
- DIFFERENT: 비교 가능한 표기가 있지만 일치하지 않는다. 다른 사람이라는 판정은 아니다.
- CONTACT_MATCH_NAME_DIFFERS: 연락처가 일치하지만 이름은 등록 표기와 다르다.
- SHARED_EMAIL / SHARED_PHONE: 해당 언급의 연락처가 여러 인물에 일치한다.
- CONTACT_TARGETS_DISAGREE: 이메일·전화가 각각 대장에 일치하나 공통 인물이 없다.
  공통 인물이 있어도 공유 연락처 경고는 유지하며 유일한 상대라고 단정하지 않는다.

compare_people는 제공받은 대장 범위 안에서만 공유·충돌을 찾는다. 한 명씩 호출하는
compare_person만으로 다른 인물의 연락처 중복을 확인할 수는 없다. 중복 personId는 오류로 알린다.
반환 순서는 대장 입력 순서이며 후보 순위가 아니다.
직함·채널·원본 ID·정답 메타데이터는 식별 단서에 넣지 않는다.
이름 유사도는 아래 12절, 후보 선별은 11절에 구현 상태를 정리했다.
임베딩·확률 점수·최종 판정은 아직 없다.

## 11. 내부 검토 후보 모으기

회사 일치는 추가 근거이며 회사·직함만 같은 사람은 포함하지 않는다.
이름이 같고 회사가 달라도 다른 사람이라고 단정하지 않고 비교 결과와 함께 남긴다.

```python
from app.identity.candidates import find_candidates

for candidate in find_candidates(mention, persons):

```

목록은 입력 대장 순서다. 3명을 넘는 동명이인도 임의 삭제하지 않는다.

## 12. 이름 유사도와 오타 검사

`similarity.py`에서 정규화한 두 이름 사이의 편집 거리를 계산한다.
편집 거리는 한 글자 삽입·삭제·교체를 각각 1회로 셌을 때 필요한 최소 횟수다.
유사도는 `1 - 편집 거리 / 두 이름 중 긴 쪽 길이`로 계산한다.
예를 들어 `가상인믈_0001`과 `가상인물_0001`은 한 글자가 달라 거리 1, 유사도 약 0.889다.
한글은 NFC로 정리한 문자 단위이며 자모·발음·영문 이름 자동 변환은 다루지 않는다.

```python
comparison = compare_person(mention, person)
print(comparison.name_similarity)  # 대표 이름/등록 별칭 중 최대 유사도, 비교 불가면 None
for item in comparison.name_similarities:
    print(item.path, item.observed, item.registered, item.edit_distance, item.similarity)
```

대표 이름과 등록 별칭 각각의 원문·필드 경로·거리·유사도를 보존한다.
빈 값과 호칭만 남은 입력은 비교 자료를 만들지 않는다. 빈 값끼리 1점을 주지 않는다.
원문과 Person 대장은 변경하지 않는다. 추가 의존성·네트워크는 없다.

**이름 유사도는 동일 인물 확률이 아니다.** 공통 접두어가 긴 가짜 이름에서는
`가상인물_0001`과 `가상인물_0002`도 약 0.889다. 오타와 다른 사람을 유사도만으로 구별할 수 없다.
name.status의 정확한 일치 판정·후보 포함 기준·충돌 경고는 변경하지 않았다.
임계값·유사도 순위·확률 점수·자동 확정은 추가하지 않았다.
오타 때문에 정확 일치 후보에서 누락되는 문제는 별도 평가 후 처리할 사항이다.

## 13. 유사도 검색·내부 순위·평가

기존 find_candidates는 정확 일치 기준으로 유지한다. 새 `ranking.py`의 rank_candidates가

```python

# 임계값은 학습 데이터에서 선택한 실험값. 기본 None이면 유사도 후보 추가 안 함.

```

추가 후보 조건: 정확 일치 단서는 없지만 현재/이전 회사가 일치하고,
대표 이름 또는 등록 별칭과의 유사도가 기준 이상이며 양쪽 이름이 각각 4자 이상이다.
짧은 이름을 유사도만으로 연결하지 않는다. 4자는 초기 보수적 설계값이며 검증된 최적값은 아니다.

순위는 연락처 일치 개수 → 정확한 이름 일치 → 현재/이전 회사 일치 → 이름 유사도 순이다.
priority는 이 우선순위를 담은 내부 튜플이며 동일 인물 확률·API score가 아니다.
