# A — 실패 사례·속도 분석

기준은 기존 학습에서 정한 이름 유사도 0.88로 고정했다. 분석 결과로 검색 코드를 바꾸거나
새 기준을 선택하지 않았다. 새 holdout/v1은 읽거나 검색 평가에 사용하지 않았다.
이번 테스트 전체는 **256 passed, 5 warnings**이며 기존 라이브러리 경고다.

## 다시 실행

ai-module/에서 기존 테스트용 Python으로 실행한다. 추가 라이브러리·모델·네트워크는 필요 없다.

```bash
python -m ml.identity.analyze_failures
python -m ml.identity.benchmark_candidates
python -m pytest tests ml/identity app/identity -q
```

기본 보고서는 results/failure_analysis.json과 results/candidate_benchmark.json이다.
재실행하면 해당 보고서를 덮어쓴다. `--output /tmp/report.json`으로 별도 저장할 수 있다.
기존 인물·비교 쌍·검증 자료는 변경하지 않는다.
벤치마크는 `--sizes 60 120 300 1000 --repeats 3`가 기본값이다.

## 무엇을 놓치고 무엇을 더 보여주나

| 기존 자료 | 정확 일치만 | 유사도 포함 규칙 |
| --- | ---: | ---: |
| 학습 2,400건의 정답 누락 | 200건 | 0건 |
| 학습의 1위 보장 실패(동점·후순위 포함) | 270건 | 70건 |
| 평가 600건의 정답 누락 | 50건 | 0건 |
| 평가의 정답 외 후보가 있는 언급 | 129건 | 150건 |
| 평가의 정답 외 후보 수 합계 | 129명 | 157명 |

정확 일치에서 빠진 것은 생성된 오타 사례다. 유사도 규칙은 이를 찾지만 다른 번호의 이름도
함께 후보에 넣는다. 평가의 추가 후보 157명은 아래 조건으로 들어왔다.

- 129명: 정확한 이름은 일치하나 회사 일치 근거는 없음(미일치 또는 누락).
- 28명: 비슷한 이름과 현재/이전 회사가 함께 일치.

이 조건은 **후보가 포함된 코드상 근거**이며 실제 사용 실패의 통계적 원인 분석은 아니다.
원문·정답 ID·추가 후보 ID·일치 경로·이름 유사도·경고가 보고서의 유형별 samples에 있다.
이름만 같은 사람을 무조건 지우면 소속이 누락된 진짜 상대도 놓칠 수 있으므로 자동 제외하지 않았다.

600건에서 정답이 항상 1위였어도 다른 후보가 남아 있으므로 자동 확정 근거가 되지 않는다.
학습의 70건은 현재 우선순위로 정답의 단독 1위를 보장하지 못했다. 동점은 personId의
우연한 표시 순서로 성공 처리하지 않았다. 동점·정보 부족은 사람이 확인할 사항이다.

이 분석은 매 쌍의 mentionB와 대장을 비교한다. 양성/음성 여부와 무관하게 검색 정답은
personIdB다. 학습 2,400건은 서로 다른 관측 단서 1,164개, 평가 600건은 286개를 포함한다.
반복을 포함한 건수라 독립된 실제 메모 수로 해석하면 안 된다.
기존 쌍별 평가의 거짓 후보 포함 101/300과 여기의 추가 후보 157명은 집계 단위가 다르다.
101은 지정된 A 인물을 잘못 후보에 넣은 음성 쌍 수이며, 157은 B 검색의 모든 정답 외 후보 수다.
외부 자동 확정 오류율은 어느 쪽에서도 측정하지 않았다.

## 규칙 검색 시간

측정 환경: Python 3.13.9, macOS Darwin 24.6.0, arm64, 논리 CPU 8개.
학습의 9유형에서 언급을 각 1건 골라 크기·캐시 상태별 3회씩, 총 27회 측정했다.
단일 프로세스에서 `rank_candidates` 전체를 호출했다.

| 대장 | 캐시 없음 중앙값 / p95 | 캐시 있음 중앙값 / p95 |
| --- | ---: | ---: |
| 60명 | 2.46 / 3.76ms | 1.20 / 1.31ms |
| 120명 | 5.21 / 7.81ms | 2.39 / 2.60ms |
| 300명 | 13.93 / 20.41ms | 6.30 / 6.82ms |
| 1,000명 | 47.73 / 76.82ms | 17.52 / 19.03ms |

중앙값은 측정치 가운데 값이고, p95는 정렬된 27개 측정치의 95% 지점이다.
표본이 적으므로 안정적인 서비스 지연 목표를 의미하지 않는다.
캐시 없음은 요청마다 편집 거리 캐시만 비운 상태, 캐시 있음은 같은 요청을 한 번 실행한 뒤다.
OS·파일 캐시나 프로세스 전체를 초기화한 부팅 시간과는 다르다. 캐시 비우기·준비 실행은 시간에서 제외했다.
300명 캐시 없음 측정의 최댓값은 55.18ms였다. 개별 지연 튐도 있어 중앙값만 보장으로 읽으면 안 된다.

60/120명은 기존 대장의 앞부분이고 1,000명은 기존 300명에 별도 가짜 부하 인물 700명을 추가했다.
작은 대장에는 입력의 실제 상대가 없을 수도 있다. 이 측정은 검색 품질 평가가 아니다.
규칙 입력만 사용했으며 모델 로딩·임베딩 추론·HTTP·DB·동시 요청은 포함하지 않았다.
BGE-M3의 앞선 약 122초는 전체 실험 실행 시간으로, 위 요청당 검색 시간과 직접 비교할 수 없다.

별도 300명 프로파일에서 편집 거리 계산의 누적 시간은 약 0.296초/검색 전체 0.520초였다.
현재는 전체 인물의 이름·별칭을 순회하며 비교하는 비용이 크다. 향후 더 큰 대장에서 문제가
확인되면 대장 정규화 재사용·연락처/이름 색인을 검토할 수 있다. 이번에는 최적화 코드를 추가하지 않았다.
프로파일러 비용은 위 시간 표에 섞지 않았으며, 함수별 누적 시간은 서로 포함되므로 더하지 않는다.

## 남은 확인

- 정답·추가 후보의 팀원 교차 검수는 아직 하지 않았다.
- 자연어 인명·다양한 오타·신규/정보 부족에 대한 실제 성능은 이 자료로 알 수 없다.
- 새 holdout은 모호한 정답 집합·충돌·신규·정보 부족을 구분하는 평가기가 필요하다.
- 실제 API/DB 연결과 동시 요청 성능은 담당자와 연결 범위를 공유한 뒤 별도로 측정한다.
- 결과가 좋아 보여도 확률 점수·CONFIRMED 정책은 임의로 확정하지 않는다.
